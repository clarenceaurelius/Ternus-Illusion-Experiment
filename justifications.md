## Justifications

Firstly, I replaced all the configuration constants and placed their assignment at the top of the document using capitalisation naming convention to distinguish from variable names, which I also defined separately. This is done for readability but also to be able to adjust, add or change variables and constant values for future experiments and development runs. These paramaters, relating to colours, positions, ISIs, repetition instances, were later moved to a separate `config.py` file and thus imported to the main `Ternus.py` to ensure changing/edits happen in one separate file. This was done as seen in class. Secondly, manual work was replaced with Expyriment methods, for instance, the randomisation of dot and shape trial order was replaced by `shuffle_trials()` method. Another improvement was to replace the for loop for trial construction with `add_trials_full_factorial()` which will construct trial design based on `number of latencies`$\times$ `number of repetitions` per block. Another feature added, was a specific development mode based on a simple if-statement, which lowered the trial repetitions from 5 to 2, made the interface window smaller, and saved the results into a `dev`folder for better organisation, in accordance with `Roth et al (2025)`'s Principle 9 (Build a shared knowledge base). I also followed the software engineering principle of making small separate commits such that each change can be reviewed and undone more easily since drastic changes are more difficult and time-consuming to reverse, which relates to Principle 2 (Track Changes) and 6 (Think about oders). I also followed the "prototyping mode" mentioned in the paper making sure the code works with changes before adding ad-hoc features like folder-structure to promote future collaboration and structure.
